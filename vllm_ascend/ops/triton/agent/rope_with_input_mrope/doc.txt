● 现在让我深入分析原始算子和参考优化版本的关键差异，确定优化方向：

  原始算子 (split_qkv_rmsnorm_rope.py) 的问题分析：

  1. 2D Grid 调用：使用 (n_rows, n_cols, 1) 的 Grid，Grid 大小与输入形状关联 →
  必须改为固定 grid = (get_vectorcore_num(),)
  2. 逐 Token 处理：在循环中每次只处理 1 个 token → 应批量处理多 Token
  3. Q/K/V 分为 3 个独立循环：Q、K、V 分开 3 个循环处理 → 应合并到同一循环内
  4. 使用 tl.load(..., mask=..., other=0.0)：带 other 参数的 load 会内部触发
  tl.where → 需要消除
  5. batch_size 未加入 do_not_specialize：可能触发重编译
  6. cos/sin 通过 pos_ptr 间接寻址（index_select）：需逐行加载
  7. RoPE 部分使用两次 insert_slice 拼接结果 → 可优化

  参考优化版本 (mrope_opt.py) 的关键优化手段：

  1. 1D Grid = (get_vectorcore_num(),)，固定大小
  2. do_not_specialize 对可变参数
  3. Token 均匀分配：front_core_num + tail_core_num 均衡分配
  4. Q/K/V 在同一循环内处理
  5. 加载与计算交织

  一、Grid 策略重构：从数据耦合 2D Grid 到固定 1D Grid

  基线问题：

  n_rows = num_vectorcore // n_cols           # 依赖 n_cols
  split_qkv_rmsnorm_rope_kernel[(n_rows, n_cols, 1)](...)
  原始代码使用 3D Grid (n_rows, n_cols, 1)，其中 n_cols 由 kv_hidden_size // 
  KV_BLOCK_SIZE 计算得出。例如当 num_kv_heads=4, head_size=128 时 n_cols=4, 
  n_rows=10（40 核设备）。Grid 的行列维度都与输入的 hidden size
  紧密耦合，同时还有 assert num_vectorcore % n_cols == 0
  这样的硬约束，限制了泛化性。

  优化方案（参考 mrope_opt）：

  grid = (block_dim,)  # block_dim ≤ core_num，固定大小
  split_qkv_rmsnorm_rope_kernel[(block_dim,)](...)
  改为纯 1D Grid，Grid 大小仅由 NPU
  物理核心数决定，与输入数据形状完全解耦。同时去掉了 assert num_vectorcore % 
  n_cols == 0 和 assert head_dim == KV_BLOCK_SIZE 这两个硬约束，提升泛化性。

  二、Token 均衡分配策略：从 stride 遍历到 front/tail 连续分段

  基线问题：

  row_step = tl.num_programs(0)  # = n_rows
  for row_idx in tl.range(row_pid, batch_size, row_step):
      # 核 0 处理 token 0, 10, 20, ...
      # 核 1 处理 token 1, 11, 21, ...
  原始代码中每个核以 row_step 为步长跳跃遍历
  token，造成不连续的内存访问模式，不利于 MTE 的 prefetch 和 cache 命中。

  优化方案（参考 mrope_opt 的 front/tail core 分配）：
  # 优化后：连续分段分配
  front_core_num = batch_size % core_num if batch_size % core_num != 0 else
  core_num
  num_tokens_each_front_core = (batch_size + core_num - 1) // core_num  # 多一个
  num_tokens_each_tail_core = batch_size // core_num                     # 
  少一个

  # 核内连续处理一段 token
  block_offset = ...  # 每个核分到一段连续区间
  for index in range(loop_num):
      token_idx = block_offset + index  # 连续递增
  - front core（前 front_core_num 个核）：每个处理 num_tokens_each_front_core 个
   token
  - tail core（剩余核）：每个处理 num_tokens_each_tail_core 个 token（比 front
  少 1 个）
  - 每个核处理的 token 在内存中是连续的，对 MTE 更友好
  - 负载均衡：前后核的 token 数量最多差 1

  三、避免重编译：do_not_specialize 修饰

  基线问题：
  @triton.jit   # 无 do_not_specialize
  def split_qkv_rmsnorm_rope_kernel(
      ...
      batch_size,   # 每次 batch_size 变化都会触发重编译
  原始代码使用裸 @triton.jit，没有 do_not_specialize。batch_size
  作为普通标量参数传入，Triton 编译器默认会对其进行特化——即每遇到一个新的
  batch_size 值，就会触发一次秒级的重编译。在推理服务中 batch_size
  频繁变化，重编译开销极大。

  优化方案：
  @triton.jit(
      do_not_specialize=["batch_size", "front_core_num",
                         "num_tokens_each_front_core", 
  "num_tokens_each_tail_core"]
  )
  对所有会随推理动态变化的标量参数添加 do_not_specialize，告诉编译器不对这些值进
  行特化优化，从而避免重编译。同时，模型结构相关的参数（q_hidden_size,
  kv_hidden_size, HEAD_DIM, NUM_Q_HEADS 等）保持为
  tl.constexpr，让编译器对这些不变值进行充分优化。

  四、三循环合并为单循环：减少循环开销和冗余计算

  基线问题：
  # 基线：3 个独立循环，串行处理 Q → K → V
  # 循环 1: Q 的 RMSNorm + RoPE + Store (遍历所有 token)
  for row_idx in tl.range(row_pid, batch_size, row_step):
      # 加载 Q 部分 → RMSNorm → RoPE → 存储 Q
      ...

  # 循环 2: K 的 RMSNorm + RoPE + Store (再次遍历所有 token)
  for row_idx in tl.range(row_pid, batch_size, row_step):
      # 加载 K 部分 → RMSNorm → RoPE → 存储 K
      ...

  # 循环 3: V 的直通 Copy (第三次遍历所有 token)
  for _ in tl.range(row_pid, batch_size, row_step):
      # 加载 V → 存储 V
      ...
  原始代码将同一个 token 的 Q/K/V 处理拆分到 3 个独立循环中，导致：
  1. 3 倍循环控制开销：循环初始化、索引计算、条件判断各执行 3 次
  2. 重复的 Scalar 地址计算：input_offset, output_offset 等在每个循环中重新计算
  3. cos/sin 重复加载：Q 循环和 K 循环各独立加载一次相同的 cos/sin
  4. 权重重新加载：K 循环开头需要重新加载 k_weight（覆盖之前加载的 q_weight）

  优化方案：
  # 优化后：单循环处理 Q + K + V
  q_weight_values = tl.load(q_weight_ptr + ...)  # 循环外一次性加载 Q 权重
  k_weight_values = tl.load(k_weight_ptr + ...)  # 循环外一次性加载 K 权重

  for index in range(loop_num):
      token_idx = block_offset + index
      in_base = input_ptr + token_idx * total_hidden_size

      in_q = tl.load(in_base + tl.arange(0, q_hidden_size))         # 加载 Q
      in_k = tl.load(in_base + q_hidden_size + tl.arange(0, ...))   # 加载 K
      in_v = tl.load(in_base + q_hidden_size + kv_hidden_size + ...) # 加载 V
      tl.store(v_ptr + ..., in_v)   # V 立即写出

      # cos/sin 只加载一次，Q 和 K 共享
      cos = tl.load(cos_sin_ptr + ...)
      sin = tl.load(cos_sin_ptr + ...)

      # Q RMSNorm + RoPE → store Q
      # K RMSNorm + RoPE → store K
  优化后的单循环中：
  - Q/K 权重在循环外一次性加载，避免循环内重复加载
  - 同一 token 的 cos/sin 只加载一次，Q 和 K 共享
  - 减少了 2 个循环的控制开销和 Scalar 地址计算

  五、消除带 other 的 tl.load：改善 MTE/Vector 流水并行

  基线问题：
  # 基线：所有 load 都带 mask 和 other=0.0
  col_indices = col_pid * Q_BLOCK_SIZE + tl.arange(0, Q_BLOCK_SIZE)
  valid_mask = col_indices < q_hidden_size
  input_values = tl.load(input_ptr + input_offset + col_indices,
  mask=valid_mask, other=0.0)
  原始代码中每个 tl.load 都使用了 mask=valid_mask, other=0.0。根据昇腾 NPU
  的硬件约束文档：
  - tl.load with other 会在内部触发 tl.where 操作
  - 这导致 MTE（数据搬运引擎）在 load 完成后需要等待 Vector（向量计算引擎）执行
  tl.where
  - 被 tl.where 阻断后，该 load 无法与后续的 load 并行执行
  - 破坏了 MTE/Vector 流水并行，成为性能瓶颈

  优化方案：

  in_q = tl.load(in_base + tl.arange(0, q_hidden_size))            # 连续 
  load，无 mask
  in_k = tl.load(in_base + q_hidden_size + tl.arange(0, kv_hidden_size))  # 连续
   load
  in_v = tl.load(in_base + q_hidden_size + kv_hidden_size + tl.arange(0,
  kv_hidden_size))
  由于改为每个核处理完整的一行 token（所有 heads），加载的数据恰好是
  q_hidden_size、kv_hidden_size 这样精确对齐的连续内存，完全不需要 mask 和 
  other。多个连续 tl.load 可以被 MTE 流水线执行，与 Vector 计算并行。

  六、消除带 mask 的 tl.store

  基线问题：
  # 基线
  tl.store(q_ptr + output_offset + col_indices,
           roped_q.reshape(Q_BLOCK_SIZE).to(q_ptr.dtype.element_ty),
           mask=valid_mask)  # 带 mask 的 store
  tl.store(v_ptr + ..., input_values, mask=valid_mask)  # 带 mask 的 store

  优化方案：
  # 优化后：无 mask 的 store
  tl.store(q_ptr + token_idx * q_hidden_size + tl.arange(0, q_hidden_size),
           roped_q.reshape(q_hidden_size))  # 无 mask
  tl.store(v_ptr + token_idx * kv_hidden_size + tl.arange(0, kv_hidden_size),
  in_v)
  与 load 同理，由于处理完整行数据，store 的长度恰好等于 q_hidden_size /
  kv_hidden_size，不需要 mask，避免 MTE 等待 Vector 生成 mask 值。

  七、边计算边写入：减少 UB 同时存活变量

  基线问题：
  # 基线：Q/K/V 各自独立循环，V 在最后一个循环才写出
  # V 的数据在输入加载时就可以直接写出，但原始代码放到了第三个循环中

  优化方案：
  # 1. V 加载后立即写出（无需计算，直通 copy）
  in_v = tl.load(in_base + q_hidden_size + kv_hidden_size + tl.arange(0,
  kv_hidden_size))
  tl.store(v_ptr + token_idx * kv_hidden_size + tl.arange(0, kv_hidden_size),
  in_v)
  # in_v 的 UB 空间立即可被释放

  # 2. Q RoPE 完成后立即 store Q，再计算 K RoPE
  roped_q = ...
  tl.store(q_ptr + ..., roped_q.reshape(q_hidden_size))  # Q 先写出
  # roped_q 的 UB 空间释放，用于后续 K 的计算

  # 3. K RoPE 完成后 store K
  roped_k = ...
  tl.store(k_ptr + ..., roped_k.reshape(kv_hidden_size))
  遵循"边计算边写入"原则（skill 文档第 8
  条），写入流通常不会冲突，提前写入可以：
  1. 释放 UB 空间给后续计算使用
  2. 增大 MTE 写出与 Vector 计算的并行可能

  八、Kernel 入参优化：语义化 constexpr

  基线问题：

  Q_BLOCK_SIZE: tl.constexpr,   # = q_hidden_size // kv_hidden_size * head_dim
  KV_BLOCK_SIZE: tl.constexpr,  # = head_dim（但语义不直观）

  Q_BLOCK_SIZE // HEAD_DIM。好处：
  - 语义更清晰，代码可读性提升
  - 编译器可以更好地优化 constexpr 参数
  - 消除了 kernel 内的 Q_BLOCK_SIZE // HEAD_DIM 除法 Scalar 运算

  九、减少 Kernel 内 Scalar 运算：直接计算地址

  基线问题：
  # 基线：使用累加式地址更新
  input_offset = row_pid * total_hidden_size
  input_offset_step = row_step * total_hidden_size
  for row_idx in tl.range(row_pid, batch_size, row_step):
      ...
      input_offset += input_offset_step   # 每次循环累加
      output_offset += output_offset_step
  原始代码在循环外预计算 offset 和
  step，然后在循环内累加。这种方式让每次迭代的地址依赖前一次迭代的结果，形成了循
  环间的数据依赖链，阻碍编译器做循环间的流水优化（troubleshooting 文档第 1.1
  节指出的流水异常原因）。

  优化方案：
  # 优化后：每次循环独立计算地址
  for index in range(loop_num):
      token_idx = block_offset + index                      # 独立计算
      in_base = input_ptr + token_idx * total_hidden_size   # 直接从 token_idx 
  算出
  每次迭代的地址通过 token_idx
  直接计算得出，不依赖前一次迭代的结果，消除了循环间的 Scalar
  数据依赖链，有利于编译器做循环流水优化。

  十、cos/sin 地址计算精简

  基线问题：
  # 基线：cos 和 sin 的地址分别用 pos_idx 计算两个 offset
  pos_idx = tl.load(pos_ptr + row_idx).to(tl.int64)
  cos_offsets = pos_idx * HEAD_DIM + tl.arange(0, HALF_HEAD_DIM)      # Scalar *
   constexpr
  sin_offsets = pos_idx * HEAD_DIM + tl.arange(HALF_HEAD_DIM, HEAD_DIM) # 
  重复计算 pos_idx * HEAD_DIM
  cos = tl.load(cos_sin_ptr + cos_offsets).reshape(1, HALF_HEAD_DIM)
  sin = tl.load(cos_sin_ptr + sin_offsets).reshape(1, HALF_HEAD_DIM)

  优化方案：
  # 优化后：cos_base 只算一次，cos 和 sin 共用
  pos_idx = tl.load(pos_ptr + token_idx).to(tl.int64)
  cos_base = pos_idx * HEAD_DIM                                         # 
  只算一次
  cos = tl.load(cos_sin_ptr + cos_base + tl.arange(0, HALF_HEAD_DIM)).reshape(1,
   HALF_HEAD_DIM)
  sin = tl.load(cos_sin_ptr + cos_base + tl.arange(HALF_HEAD_DIM,
  HEAD_DIM)).reshape(1, HALF_HEAD_DIM)
  将 pos_idx * HEAD_DIM 提取为公共变量 cos_base，减少一次 Scalar 乘法。

  十一、Host 端的简化：去除硬约束 assert

  基线问题：
  # 基线 impl 中的硬约束
  KV_BLOCK_SIZE = triton.next_power_of_2(head_dim)
  assert head_dim == KV_BLOCK_SIZE          # 要求 head_dim 必须是 2 的幂
  assert q_hidden_size % kv_hidden_size == 0  # 要求可整除
  n_cols = kv_hidden_size // KV_BLOCK_SIZE
  assert num_vectorcore % n_cols == 0       # 要求核心数能被 n_cols 整除
  这三个 assert 严重限制了算子的适用场景。例如 num_vectorcore % n_cols == 0 要求
   NPU 核心数必须能被 kv_heads 整除。

  优化方案：
  # 优化后：无硬约束，自适应分配
  core_num = get_vectorcore_num()
  front_core_num = core_num
  if batch_size % core_num != 0:
      front_core_num = batch_size % core_num
  # ... 无 assert
  通过 front/tail core
  的弹性分配策略，完全消除了对输入形状的硬约束，提升泛化性。
