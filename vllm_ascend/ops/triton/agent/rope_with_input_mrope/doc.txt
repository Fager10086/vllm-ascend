  现在让我深入分析原始版本和优化版本的差异，提炼优化策略：

  原始 mrope.py 的问题（与当前 rope.py 类似）：
  1. 逐 token 处理，每次循环仅处理 1 个 token
  2. Grid 使用 min(core_num, batch_size)，与输入形状相关
  3. 没有使用 do_not_specialize
  4. 大量带 other 参数的 tl.load
  5. Q、K、V 分开循环处理

  优化后 mrope_opt.py 的关键手段：
  1. 1D Grid = (get_vectorcore_num(), )，固定大小
  2. do_not_specialize=["batch_size"] 避免重编译
  3. 多 Token 并行处理：通过 UB 容量规划，一次循环处理多个 token
  4. Q 和 K 在同一循环中处理（只 load 一次 input，合并 Q+K 为 qk_size）
  5. V 单独循环（也是多 token 批量处理）
  6. 消除带 other 的 tl.load
  7. 预计算所有参数偏移量在 host 端传入 kernel 作为 constexpr

  现在我来实现优化版本。当前 rope.py 的关键参数：
  - head_size = 128, total_hidden_size = q_hidden_size + 2 * kv_hidden_size
  - 对于 (32,4): q_hidden_size=4096, kv_hidden_size=512, total_hidden_size=5120
  - Q_BLOCK_SIZE = (q_hidden_size/kv_hidden_size) * head_size = 8*128 = 1024
  - cos_sin_cache: [max_pos, head_size] 其中 head_size=128

  UB 容量规划（rope 版本，参考 mrope_opt）：
  - 输入 load: batch_size_per_iter * (num_q_heads + num_kv_heads) * head_size
  (qk 部分)
  - 中间变量 normalized_values: fp32, 同样大小 ×2
  - cos/sin: batch_size_per_iter * head_size (每个token一对 cos/sin)
  - RoPE 中间计算: x1, x2, roped_q 等

  核心优化手段总结：

  1. 1D Grid 固定大小：grid = (get_vectorcore_num(), ) → 不依赖 batch_size
  2. do_not_specialize=["batch_size"]：避免 batch_size 变化导致重编译

  5. V 单独多 token 批处理
  6. 所有偏移量在 host 端预计算，作为 constexpr 传入
  7. cos/sin 使用 tl.arange 生成索引进行连续读取

  对于 rope.py 的特殊差异（与 mrope 不同）：
  - rope 使用 pos_ptr (positions) + cos_sin_cache 进行
  index_select（离散访问），而 mrope 的 cos_sin 数据已经是连续的
  - rope 中 cos_sin_cache 是 [max_position_embeddings, head_size]，通过
  positions 索引取行

  1. 当前版本加载 cos/sin 时使用了 pos_indices 的离散地址访问，需要通过
  cur_mblk_idx 先加载 positions 再计算索引，引入了大量 Scalar 计算
  2. 多 token 并行加载 cos/sin 的方式对于离散的 index_select 效率不高

  让我重新审视方案。关键问题是 cos_sin_cache 的访问模式：原始代码逐个 token 的
  tl.load(pos_ptr + row_idx) 然后用 pos_idx 访问 cos_sin_cache，这是离散的。

  根据优化指南第 6 条："对于 index_select 这类涉及非连续地址访问的操作，只能通过
  循环逐行读取数据"。所以我需要在循环中逐行加载 cos/sin，而不是用二维索引。

  但同时，关键优化在于 Q+K 合并加载、减少循环次数。让我重新设计，把 cos/sin
  的加载改为逐行循环方式，同时仍保持多 token 的 QK 合并处理。

  实际上，重新思考后，更好的方案是：保持多 token 的 Q+K 合并
  load（这是最大的性能提升），但对 cos/sin 逐 token 循环加载后整合到 3D tensor

  ---
  优化要点全面详细总结

  一、Grid 策略优化：从形状相关的 2D/3D Grid → 固定大小的 1D Grid

  原始代码：
  n_cols = kv_hidden_size // KV_BLOCK_SIZE   # 依赖输入 shape
  n_rows = num_vectorcore // n_cols
  split_qkv_rmsnorm_rope_kernel[(n_rows, n_cols, 1)](...)
  Grid 大小 (n_rows, n_cols, 1) 与 kv_hidden_size 直接关联：当 num_kv_heads=1 时
   n_cols=1、n_rows=20；当 num_kv_heads=4 时
  n_cols=4、n_rows=5。这意味着不同的输入配置会产生不同的 Grid 形状。

  优化后：
  grid = (core_num, )   # 固定为 get_vectorcore_num()
  split_qkv_rmsnorm_rope_kernel[grid](...)
  1D Grid 固定大小，完全不依赖输入数据的 shape。消除了 col_pid = 
  tl.program_id(1) 以及由此衍生的所有列方向 Scalar 运算（col_pid * 
  Q_BLOCK_SIZE、valid_mask = col_indices < q_hidden_size
  等），这些每次循环迭代都要执行的 Scalar 计算在 Ascend NPU
  上开销显著。同时也消除了 host 端 n_cols、n_rows 的计算以及 assert 
  num_vectorcore % n_cols == 0 的约束检查。

  ---
  二、避免重编译：添加 do_not_specialize

  原始代码：
  @triton.jit
  def split_qkv_rmsnorm_rope_kernel(..., batch_size, ...):
  batch_size 作为普通参数，Triton 编译器会对其值进行特化。每当 batch_size
  变化（如 1→4→8→16→1024），Triton
  会触发重新编译，编译耗时秒级，严重影响首次调用和变长输入场景的性能。

  优化后：
  @triton.jit(do_not_specialize=["batch_size"])
  def split_qkv_rmsnorm_rope_kernel(..., batch_size, ...):
  通过 do_not_specialize 声明 batch_size
  为不特化参数。编译器不再为其生成专用代码，只编译一次即可适配任意
  batch_size，避免了频繁重编译。

  ---
  三、核心循环架构重构：三段独立循环 → 单循环融合

  原始代码有三个独立循环，共遍历输入数据三次：

  1. Q 循环（第 60–118 行）：遍历所有 token，加载 Q 部分 → RMSNorm → RoPE → 存储
   Q
  2. K 循环（第 126–184 行）：遍历所有 token，加载 K 部分 → RMSNorm → RoPE →
  存储 K
  3. V 循环（第 188–194 行）：遍历所有 token，加载 V 部分 → 直接存储 V

  每个循环独立访问全局内存读取各自的数据段，加上 col_pid
  的列分块，导致同一行数据在 Q 循环和 K
  循环中被分别访问了两次（偏移不同），cos/sin 也被重复加载两次（Q 和 K 的 RoPE
  使用相同的 cos/sin）。

  优化后合并为单循环：
  for row_idx in tl.range(input_batch_offset, input_batch_offset_end):
      # 1. 一次性加载完整行 (Q+K+V)
      all_values = tl.load(input_ptr + input_offset + all_col_indices)
      # 2. extract_slice 零拷贝分离 V 并立即写出
      v_values = tl.extract_slice(...)
      tl.store(v_ptr + ...)
      # 3. extract_slice 零拷贝分离 QK
      qk_values = tl.extract_slice(...)
      # 4. Q+K 合并 RMSNorm
      # 5. 一次加载 cos/sin
      # 6. extract_slice 分别取 Q/K 做 RoPE 并写出

  核心改进：
  - 数据只遍历一次：每个 token 的整行数据仅被 tl.load
  读取一次，替代原来的三次独立遍历
  - cos/sin 只加载一次：同一 token 的 cos/sin 由 Q 和 K 共享，不再重复读取
  - tl.extract_slice 零拷贝分片：从已加载的连续数据中切分 Q、K、V
  部分，无额外内存拷贝

  ---
  四、全行一次性加载：减少 GM 访存次数

  原始代码每次循环有多次 tl.load：
  - Q 循环中：tl.load(input_ptr + input_offset + col_indices, mask=valid_mask, 
  other=0.0) — 带 mask 和 other 的 load
  - K 循环中：同样的带 mask load
  - V 循环中：又一次带 mask load

  三次循环 × 每次一个 masked load = 对同一 token 数据做了 3 次全局内存访问。

  优化后：
  all_values = tl.load(input_ptr + input_offset + all_col_indices)
  一次无 mask 的连续 tl.load 读取整行 total_hidden_size 个元素。之后通过
  tl.extract_slice 在寄存器级别零拷贝地切分出 QK 和 V 部分。全局内存访问从 3
  次降为 1 次。

  ---
  五、消除带 other 的 tl.load

  原始代码：
  tl.load(input_ptr + input_offset + col_indices, mask=valid_mask, other=0.0)
  other=0.0 参数会在 load 内部触发 tl.where 操作，根据 Ascend NPU
  优化指南，这会阻止 load 与其他 load 并行执行，降低流水线效率。

  优化后：
  tl.load(input_ptr + input_offset + all_col_indices)
  所有 QKV load 均为无 mask、无 other 的直接连续 load。由于每个 core 处理的
  token 范围通过 batch_size_per_vec 精确划分，循环边界 input_batch_offset_end = 
  min(...) 保证了不会越界，无需 mask 保护。

  ---
  六、Q+K 合并 RMSNorm

  原始代码分别做 Q 和 K 的 RMSNorm：
  - Q 循环中：对 (Q_BLOCK_SIZE // HEAD_DIM, HEAD_DIM) 做 RMSNorm
  - K 循环中：对 (KV_BLOCK_SIZE // HEAD_DIM, HEAD_DIM) 做 RMSNorm

  两次独立的 squares → sum → sqrt → reciprocal 运算。

  优化后合并为一次：
  qk_values = qk_values.reshape(num_qk_heads, HEAD_DIM)  # (num_q_heads + 
  num_kv_heads, HEAD_DIM)
  normalized_values = qk_values.to(tl.float32)
  squares = normalized_values * normalized_values
  variances = tl.sum(squares, axis=1) / HEAD_DIM
  reciprocal_std = (1 / tl.sqrt(variances + eps)).reshape(num_qk_heads, 1)
  normalized_values = qk_values * reciprocal_std
  Q 和 K 的所有 head 拼接成 (num_qk_heads, HEAD_DIM) 一次性做 RMSNorm。之后通过
  tl.extract_slice 分别取出 Q 部分 [0:num_q_heads] 和 K 部分
  [num_q_heads:num_qk_heads] 应用各自的 weight/bias。这减少了一半的 RMSNorm
  规约运算（tl.sum、tl.sqrt）。

  ---
  七、V 写入流提前 (Write Interleaving)

  原始代码： V 在第三个独立循环中处理，时序上在所有 Q 和 K 处理完毕之后。

  优化后：
  # 先 load 全行
  all_values = tl.load(...)
  # 立刻 extract 并 store V（此时 Q/K 的 RMSNorm 和 RoPE 还没开始）
  v_values = tl.extract_slice(...)
  tl.store(v_ptr + ...)
  # 然后才做 QK 的 RMSNorm + RoPE
  qk_values = tl.extract_slice(...)
  ...
  V 数据无需任何计算变换（直接拷贝），因此在加载完整行后立即 store V，然后再进入
   QK 的 RMSNorm/RoPE 计算。根据优化指南第 8 条
  "若存在多个写入流，建议边计算边写入数据"，V 的 store 与后续 QK
  计算之间可以形成写入-计算流水并行，MTE（Memory Transfer Engine）在搬运 V
  数据时，Vector 单元可以同时执行 RMSNorm 计算。

  ---
  八、消除循环内的 col_pid 相关 Scalar 计算

  原始代码每次循环迭代中：
  col_indices = col_pid * Q_BLOCK_SIZE + tl.arange(0, Q_BLOCK_SIZE)
  valid_mask = col_indices < q_hidden_size
  col_pid * Q_BLOCK_SIZE 和 col_indices < q_hidden_size
  在每次迭代中执行，是与循环变量无关但依赖 col_pid 的 Scalar 运算。

  优化后： 完全消除 col_pid，所有列索引在循环外一次性生成：
  all_col_indices = tl.arange(0, total_hidden_size)  # 循环外
  循环内不再有任何列方向的 Scalar 计算。

  ---
  九、Weight 和 Bias 只加载一次

  原始代码：
  # Q 循环前
  weight_values = tl.load(q_weight_ptr + tl.arange(0, HEAD_DIM))
  # ...Q 循环...
  # K 循环前（重新加载 k_weight 覆盖同名变量）
  weight_values = tl.load(k_weight_ptr + tl.arange(0, HEAD_DIM))
  weight_values 和 bias_values 变量名被 Q 和 K 阶段复用，K 阶段覆盖了 Q
  阶段的值。虽然总 load 次数相同（Q_weight 1 次 + K_weight 1 次），但 Q
  阶段的变量在 K 循环开始时被覆盖释放。

  优化后使用不同变量名：
  q_rmsnorm_weight = tl.load(q_weight_ptr + tl.arange(0, HEAD_DIM))
  k_rmsnorm_weight = tl.load(k_weight_ptr + tl.arange(0, HEAD_DIM))
  两组 weight 在循环外同时加载并保持到循环结束，避免了变量覆盖，同时避免了数据流
  错误的风险（遵循优化指南 "避免复用 tl.load 和 tl.store 的变量名"）。

  ---
  十、Host 端代码简化

  原始 host 端有多项约束和依赖：
  KV_BLOCK_SIZE = triton.next_power_of_2(head_dim)
  assert head_dim == KV_BLOCK_SIZE
  assert q_hidden_size % kv_hidden_size == 0
  Q_BLOCK_SIZE = q_hidden_size // kv_hidden_size * head_dim
  n_cols = kv_hidden_size // KV_BLOCK_SIZE
  assert num_vectorcore % n_cols == 0
  n_rows = num_vectorcore // n_cols
  6 行配置 + 3 个 assert，Grid 计算逻辑与多个输入参数耦合。

  优化后：
  batch_size_per_vec = triton.cdiv(batch_size, core_num)
  grid = (core_num, )
  2 行配置，无 assert 约束。Grid 固定，batch_size_per_vec
  是唯一需要计算的值，等于 ceil(batch_size / core_num)。
