# 同类算子开发优化：让 Agent 学会举一反三

> *"What I cannot create, I do not understand."*
> *—— Richard Feynman*
>
> 反过来也成立：**你真正理解的东西，一定能教会别人。**
> 问题是——能不能教会一个 Agent？

---

## 一、问题的本质

昇腾 NPU 上的 Triton 算子优化，是一门手艺活。

一个经验丰富的算子工程师，面对一个新算子，脑中会迅速完成一系列判断：Grid 该怎么绑核？UB 容量能塞下几个 Token？哪里能做访存-计算流水并行？哪些 mask 可以消掉？这些判断依赖对硬件架构的深刻理解——Scalar、MTE、Vector 三条流水线如何协作，192 KB 的 Unified Buffer 如何分配，Double Buffering 的约束在哪里。

问题在于：**这些判断具有极强的模式性。** 同一类算子——比如同属 FLA（Flash Linear Attention）的一组矩阵运算 kernel，或同属 normalization 流程的一组 Vector kernel——它们的优化手法高度相似。Grid 绑核的方式一样，持久化循环的写法一样，`do_not_specialize` 要加的参数一样，甚至连容易踩的坑（忘记恢复 T 值、多维 Grid 展开公式写反）都一样。

一个专家花一天优化好一个算子，回头看同目录下还有五个结构相似的——每个再花半天，那就是三天重复劳动。

**这就是同类算子开发优化 Skill 要解决的核心问题：能不能把专家的"手法"提炼成模板，让 Agent 去做那五个？**

---

## 二、Skill 是什么——一段被编纂的专家经验

`triton-ascend-ops-optimizer` Skill 本质上是一份**结构化的优化知识**，装在三个文件里：

| 文件 | 角色 |
|------|------|
| `SKILL.md` | 主控——定义优化目标、工作流程、13 条优化技术、约束规则 |
| `references/hardware_constraints.md` | 硬件手册——Ascend 910B 三引擎架构、UB 容量计算公式、流水线并行条件 |
| `references/troubleshooting.md` | 排错指南——7 类典型问题的诊断路径和修复方法 |

当 Agent 被激活时，它并不是在"自由发挥"——它在一套严格的框架下工作：

1. **先测基线**：分析算子结构，跑通正确性验证，记录初始性能。
2. **再做优化**：每次修改后，先验正确性，再量性能。通不过正确性，就不准量性能。
3. **按需查文档**：遇到 UB 溢出去查容量计算公式，遇到流水线断裂去查硬件约束。
4. **迭代至达标**：性能没达标就不停，达标了输出标准化报告。

更重要的是它内化的**13 条优化技术**，每一条都直指昇腾硬件的一个关键约束：

- **Grid 固定绑核**：`grid = (get_vectorcore_num(), )`，不跟数据形状走——这保证了泛化性。
- **多 Token 批处理**：不再逐 Token 访存，而是算好 UB 能装几个（N = 85×1024 // S_token），一批装满。
- **避免重编译**：`do_not_specialize` 把会变的标量参数管住，一次编译覆盖所有 batch size。
- **消除 mask 开销**：`tl.load` 不带 `other` 参数，mask 延后处理，保住 MTE/Vector 流水线。
- **加载-计算交织**："装一车算一车"，而非"全装完再算"——藏住访存延迟。

**但 Skill 单独工作时，有一个根本局限：它知道"怎么优化"，但不知道该在面前这个算子上"优化成什么样子"。** 没有具体的目标形态，生成结果容易发散——今天改访存模式，明天改 tiling 策略，每次不同，审视者无法建立信任。

## 三、关键洞察——专家模板 + Agent 仿照

解决办法出奇地简单，简单到像费曼解释物理定律时的那种简单——**给 Agent 一道例题和标准答案，让它去做同类题。**

这就是 `ascend_affinity_skill_guide.md` 所提炼的核心方法论：

```
专家手工优化 1 个算子  →  产出"改造前/改造后"模板对
                                    ↓
          Agent 拿着模板对，仿照改造 N 个同类算子
```

为什么这行得通？因为它精确地把人和机器摆在了各自最擅长的位置上：

| 角色 | 擅长 | 不擅长 |
|------|------|--------|
| **专家** | 判断、创造——发明优化手法，定义"该改什么、不该动什么"的边界 | 重复——把同一套手法机械地施加到十几个相似算子上 |
| **Agent** | 重复、精确——严格模仿一种模式，在结构相似的代码上一致地执行 | 创造——从零发明一种新的优化范式 |

模板消除了发散性。Agent 不再需要决定"怎么优化"，它只需要回答一个简单得多的问题：**"模板做了哪些改动？我面前这个算子的对应位置在哪里？"**

### 两种模板，两种改造深度

实践中，算子按计算特征分为两类，各有专属模板：

**CV 算子**（含 `tl.dot` 矩阵运算）——改造仅触碰调度层：

| 改动 | 说明 |
|------|------|
| Grid `(NT, B*H)` → `(AICORE_NUM,)` | 物理核心绑定 |
| 新增 `grid0` 参数 | 解耦物理 Grid 与逻辑工作量 |
| `for i in range(pid, grid0, core_num)` | 持久化循环 |
| `T_orig = T` + 循环内恢复 | VARLEN 模式保护 |
| **内部计算逻辑完全不动** | 纯调度优化 |

**Vector 算子**（RMSNorm、RoPE 等）——改造深入计算和访存层：

| 改动 | 说明 |
|------|------|
| 多维 Grid → 一维绑核 | 消除分块维度 |
| 三循环 → 单循环融合 | 访存 3 次 → 1 次 |
| 分块 mask → 整行无 mask | 连续 DMA 传输 |
| Q+K RMSNorm 合并 | 减少计算冗余 |
| V early-store | MTE 与 Vector 流水并行 |

## 四、价值——不只是快，而是"规模化地快"

### 效率跃迁

投入产出的不对称性，是这套范式最有力的论据：

| 阶段 | 投入 | 产出 |
|------|------|------|
| 专家优化第 1 个算子 | **高**（需硬件经验 + 多轮调试） | 1 个优化算子 + 1 个可复用模板 |
| Agent 仿照第 2～N 个 | **低**（编写 Prompt + 审视输出） | N−1 个优化算子 |

**第 1 个算子的专家投入是一次性成本，此后每个同类算子的边际成本趋近于零。**

在实战中：CV 模板（`chunk_scaled_dot_kkt`）已成功覆盖 `solve_tril`、`wy_fast` 等 FLA 目录下多个算子；Vector 模板（`split_qkv_rmsnorm_mrope`）已成功覆盖 `split_qkv_rmsnorm_rope` 等算子，单算子性能提升 2 倍以上。

### 泛化性保障

Skill 强制要求 **Grid 固定绑核**（`get_vectorcore_num()`），不随输入 shape 变化。这意味着优化后的算子天然适配不同 batch size、不同序列长度——无需为每种配置单独调优。

对大模型推理场景而言，这一点至关重要：推理服务面对的请求长度分布是动态的，一个只对 batch_size=32 表现好的算子，在生产环境中毫无意义。

### 审视成本下降

Agent 的改动被模板严格约束——改什么、不改什么、改的边界在哪里，全部由模板定义。审视者不需要理解"Agent 为什么这样改"，只需要检查"Agent 是否忠实地复现了模板模式"。

这把审视从一个开放性问题（"这段优化合不合理？"）转化为一个验证性问题（"这段改动和模板一致吗？"）——后者的认知负荷远低于前者。

## 五、最佳实践——5 步工作流

整套方法论被提炼为一个可重复执行的 5 步流程：

### Step 1：分类——这是哪类算子？

```
有 tl.dot → CV 算子 → 用 CV 模板
无 tl.dot → Vector 算子 → 用 Vector 模板
```

### Step 2：准备——找到或建立专家模板

已有模板直接用；新类型算子需专家先手工优化一个，保留**改造前+改造后**两个文件。

> 模板的价值不在于优化了多少性能，而在于它定义了一种**改造模式**。

### Step 3：编写 Prompt——四要素齐备

```
① 触发 Skill    → /triton-ascend-ops-optimizer
② 目标文件/函数  → 绝对路径 + kernel 函数名
③ 参考模板      → 改造前文件 + 改造后文件（"必须参考"而非"可以参考"）
④ 验证方式      → 正确性测试命令 + 性能测试命令
```

一个实际 Prompt 的样子：

```
使用 Skill /triton-ascend-ops-optimizer 实现算子grid改造：
/path/to/target_op.py 的 target_kernel。
优化必须参考 /path/to/template_opt.py
对 /path/to/template.py 使用的性能优化手段。
```

关键词是**"必须参考"**——这不是建议，是约束。它把 Agent 的行为空间从"无限可能"压缩到"模仿模板"。

### Step 4：执行与审视

Agent 执行后，按算子类型检查关键点：

| CV 算子审视 | Vector 算子审视 |
|-------------|-----------------|
| Grid 是否改为硬件核心数？ | 循环是否正确融合？ |
| 持久化循环是否正确？ | extract_slice 边界是否正确？ |
| 多维 Grid 展开逻辑对不对？ | mask 是否已消除？ |
| 内部计算逻辑是否保持不变？ | early-store 时序是否合理？ |

### Step 5：验证——正确性 + 性能

先跑精度测试（不过不准测性能），再跑性能测试。两项都通过，这个算子就完成了。

## 六、一个具体的例子

用案例说话。`solve_tril.py` 中的 `merge_16x16_to_64x64_inverse_kernel`，原始代码长这样：

```python
# Grid 与问题规模挂钩
merge_16x16_to_64x64_inverse_kernel[NT, B * H](...)

@triton.jit(do_not_specialize=["T"])
def merge_16x16_to_64x64_inverse_kernel(...):
    i_t, i_bh = tl.program_id(0), tl.program_id(1)
    # ... 矩阵块合并计算 ...
```

给 Agent 一句 Prompt，指向 CV 模板，Agent 自动生成：

```python
# Grid 绑定硬件核心数
grid = (AICORE_NUM,)
merge_16x16_to_64x64_inverse_kernel[grid](
    ..., grid0=NT * B * H              # 二维工作量展开为一维
)

@triton.jit(do_not_specialize=["T", "B"])
def merge_16x16_to_64x64_inverse_kernel(..., grid0=0):
    pid = tl.program_id(0)
    core_num = tl.num_programs(0)
    T_orig = T
    for i_work in range(pid, grid0, core_num):  # 持久化循环
        T = T_orig
        i_t = i_work // (B * H)                 # 反算原始二维索引
        i_bh = i_work % (B * H)
        # ... 内部计算逻辑完全不变 ...
```

注意 Agent 做对了几件不平凡的事：二维 Grid 展开为一维、索引反算公式正确、T 的保存/恢复到位、`do_not_specialize` 扩展了 `"B"`——**而内部计算逻辑一个字没动。** 这正是模板约束的力量。

## 七、结语

回到费曼那句话。同类算子优化 Skill 的本质，是**把专家的理解编码成一种可教授的形式**——不是教给学生，而是教给 Agent。

它不能替代专家（第一个算子仍需人来优化），但它把专家的能力**放大**了：一份手艺，N 份产出。

更深层地看，这提供了一种**昇腾推理优化的工作范式**：

```
人类专家 → 创造优化模式（一次性、高投入）
Agent    → 复制优化模式（规模化、低成本）
人类审视 → 验证一致性（确定性、低认知负荷）
```

这是一个**可持续的增长飞轮**——每多一种专家模板，Agent 能覆盖的算子族就多一片；每多一片被覆盖的算子族，专家就被释放出来去攻克下一种新类型。

算子优化的终极目标不是让某一个 kernel 跑得更快，而是让**整个优化过程**跑得更快。这才是同类算子开发优化 Skill 真正的价值所在。
