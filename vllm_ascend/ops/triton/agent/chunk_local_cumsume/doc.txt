  算子分析：
  - 输入 g: shape (1, T_total, H) 其中 T_total ≈ 10288, H=8, dtype=float32
  - 这是一个纯 Vector 算子（无 tl.dot），Grid 应使用 (get_vectorcore_num(), ) =
  (40, )
  - 原始 Grid 为 (num_blocks, B) = 2D Grid，且 num_blocks 与数据形状相关

  原始算子的性能瓶颈：
  1. Grid 大小与数据形状相关：grid = (num_blocks, B) 中 num_blocks =
  triton.cdiv(T, OPTIM_BLOCK_SIZE)，违反固定 Grid 大小要求
  2. 每个核只处理一个 block：没有批量处理多个 Tokens
  3. 使用了 make_block_ptr 和 tl.trans/tl.reshape：大量 reshape/transpose 操作
  4. OPTIM_BLOCK_SIZE 计算：(2**18) // (H * chunk_size) = 262144 // (8 * 64) =
  512
  5. 数据格式：(T, H) 即 (BLOCK_T, H) = (512, 8)，先 reshape 为 (N_CHUNKS, 
  CHUNK_SIZE, H) = (8, 64, 8)，再 transpose 为 (64, 8, 8)，然后 cumsum axis=0

  优化策略：
  1. 使用固定 Grid = (get_vectorcore_num(), ) = (40, )
  2. 每个核通过循环处理多个 blocks
  3. 简化内核逻辑，避免 3D reshape/transpose，直接按 chunk 处理
  4. 使用 do_not_specialize 避免重编译
  5. UB 容量规划，批量加载处理多个 tokens

  让我计算 UB 占用：
  - 每个 chunk：CHUNK_SIZE * H = 64 * 8 = 512 elements of float32 = 2048 bytes
  - 同时需要 load + compute(cumsum) + store = 2048 * 3 = 6144 bytes
  - 可用 UB = 85 * 1024 = 87040 bytes

  - 但实际上每个 chunk 只需要 load 和 store（cumsum 是 in-place），所以 S_token
  ≈ 2048 * 2 = 4096 bytes per chunk

● 理解了。在 IS_VARLEN 模式下：
  - block_indices 是一个 (num_blocks, 2) 的 tensor
  - block_indices[i] = (i_s, i_block)：i_s 是序列索引，i_block 是该序列内的
  block 索引
  - 每个 block 处理 OPTIM_BLOCK_SIZE = 512 个 tokens
  - B=1，只有一个序列，T_total=6986
  - num_blocks = cdiv(6986, 512) = 14

  关键洞察：在 IS_VARLEN 模式下，kernel 使用 chunk_indices 来索引每个
  block。但在当前实现中，Grid = (14, 1)，每个核只处理一个 block。

  优化方案：
  1. 改用固定 Grid = (40,)
  2. 每个核通过循环处理分配给它的多个 blocks（stride = 40）
  3. 避免 3D reshape + transpose + cumsum，改用直接在 2D 数据上按 chunk 进行
  cumsum
  4. 批量处理多个 tokens

● V1 结果约 0.691~0.756 ms，与基线 0.774 ms 相当。仅将 Grid 固定为 40
  核并让核内循环多个 blocks 的优化效果不明显——因为原始实现只有 14 个
  blocks，而现在 40 个核中大部分核只能分到 0 或 1 个 block。

  瓶颈在于每个 block 内部的计算效率。需要重新设计
  kernel，让每个核处理更细粒度的工作单元（按 chunk 而非按 block），并批量处理多
  tokens。

  让我重新分析：
  - 原始方案：每个 block 处理 BLOCK_T=512 个 tokens（包含 N_CHUNKS=8 个 chunk）
  - 数据形状：(BLOCK_T, H) = (512, 8)，reshape 为 (8, 64, 8)，transpose 为 (64,
  8, 8)，cumsum axis=0
  - 实际上 cumsum 是在每个 chunk_size=64 范围内做的

  关键优化思路：将工作单元改为单个 chunk（64*8=512 float32 = 2048
  bytes），每次循环批量处理多个 chunks。总共 chunks = cdiv(T_total, 64) ≈ 110 个
   chunks，40 个核均匀分配，每核 ≈ 3 个 chunks。

  粒度
  2. 使用 make_block_ptr 替代手动地址计算，避免 Scalar 开销
  3. 直接在 2D (CHUNK_SIZE, H) 上做 cumsum，不需要 3D reshape/transpose
  4. 避免 mask load，使用 boundary_check

  优化技术清单

  1. [已应用] 固定 Grid 大小：将 grid = (num_blocks, B) 改为 grid = 
  (get_vectorcore_num(), ) = (40,)，按规范使用固定 1D Grid，kernel
  内通过循环处理多个 chunks
  2. [已应用] Chunk 粒度并行：将工作单元从 BLOCK_T=512 个 tokens 细化为
  CHUNK_SIZE=64 个 tokens，使 110 个 chunks 在 40 个核上更均匀分配（每核 ~2.75
  个 chunks），提升并行度
  3. [已应用] 消除 3D reshape/transpose：原始 kernel 需要 reshape(N_CHUNKS, 
  CHUNK_SIZE, H) + trans(1,0,2) + cumsum + trans(1,0,2) + reshape；优化后直接在
  2D (CHUNK_SIZE, H) tensor 上 cumsum(axis=0)，大幅减少 Vector 计算开销
  4. [已应用] 消除 Host 端 prepare_chunk_indices 开销：原始方案每次调用都执行
  prepare_chunk_indices（~0.49 ms），优化后使用 len(cu_seqlens)
  和形状信息直接计算（~0 ms），避免 GPU 同步
  5. [已应用] 单序列路径特化：为 seq_count==1 提供简化 kernel
  chunk_local_cumsum_simple_kernel，完全消除 kernel 内的序列查找循环，减少
  Scalar 计算
  6. [已应用] 避免 GPU 同步：对 B=1 单序列场景，使用 g.shape 中的 T 替代
  cu_seqlens.tolist()，避免 NPU→CPU 数据同步开销（~0.04 ms）
  7. [已应用] do_not_specialize 避免重编译：对 total_T, total_chunks, bos_offset
   等可变标量参数使用 do_not_specialize，避免因值变化触发重编译

  关键修改说明

  - 修改点 1：重构 Grid 策略——从数据形状相关的 2D Grid (num_blocks, B)
  改为固定大小 1D Grid (get_vectorcore_num(), )，kernel 内通过 range(pid, 
  total_chunks, NUM_CORE) 循环分配任务
  - 修改点 2：拆分为两个
  kernel——chunk_local_cumsum_simple_kernel（单序列/非变长快速路径）和
  chunk_local_cumsum_scalar_kernel（多序列变长路径），根据 seq_count 在 Host
  端选择调度
  - 修改点 3：Host 端计算最小化——单序列场景完全零开销（仅用 len()
  和整数运算），多序列场景仅需 cu_seqlens.tolist() + Python 整数运算
  - 修改点 4：Kernel 内计算简化——每个 chunk 仅需 make_block_ptr → tl.load →
  tl.cumsum → tl.store，无 reshape/transpose 操作
